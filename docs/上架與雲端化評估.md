# Threads 小工具：上架 Chrome 商店與雲端化評估

寫於 2026-10-16。給 Jeff 決定用，沒有動任何插件程式。我不是律師，法律那節是整理公開資料後的讀法，真要公開營運請找人看。查證來源與日期放在最後一節；沒查到或只有二手來源的地方，文中都標「待確認」。

## 先講結論

| 問題 | 結論 |
|---|---|
| 現在這版能不能原樣上 Chrome 商店？ | 不能。至少要拿掉影片下載、換掉 Threads Logo 圖示、改掉名字裡的「Threads」、補隱私政策，而且五個功能要縮到一個「單一用途」。 |
| 精簡後能不能上？ | 技術上能過審的機率不低（商店上已有數個 Threads 抓取類插件）。真正的風險不在 Google，在 Meta：它的條款禁止未經許可的自動化抓取，而且把「登入狀態」也寫進去了。 |
| 資料雲端化對大家比較方便嗎？ | 「個人單機版上雲」方便又低風險：換電腦、讓雲端排程產每日串。「多人共用資料池」風險高，建議不做。 |
| 我的建議 | ① 先維持自用；② 想給朋友或老婆用，走「不公開（Unlisted）」或直接給 zip；③ 雲端化只做「每人只看自己的資料」的版本，先給 Jeff 自己用；④ 公開上架等①～③跑順、而且 Jeff 願意承擔 Meta 這邊的風險再說。 |

## 一、上架要改什麼

### 1.1 現況對照 Chrome 商店規則

| 現有功能或設定 | 商店規則怎麼看 | 要改什麼 |
|---|---|---|
| 影片下載（`videos` → `chrome.downloads`） | 政策禁止「協助未經授權下載或串流受著作權保護的內容」，也禁止「繞過登入或付費牆取得內容」。影片下載器雖然沒有被明文全面禁止，但只是不給「精選」資格，審查時是高風險項。 | **整個拿掉。**連同 `page-hook.js` 裡抓 `video_versions` 的部分、`background.js` 的 `videoDownloader`。 |
| 圖示：黑底金色 Threads Logo | 政策禁止侵犯他人商標，也禁止暗示得到別家公司背書。Logo 當圖示等於把 Meta 的商標當自己的品牌。 | **重畫原創圖示。**Jeff 是設計師，這項成本最低。不要用 @ 字形、纏繞的 6/@ 形狀，避免被認為是仿冒。 |
| 名稱「Threads 小工具」 | 同上，名稱用了商標。Meta 品牌守則怎麼規定第三方可不可用「Threads」在產品名稱，我這次沒查到（待確認）。保守做法是名稱不放 Threads，描述裡寫「適用於 threads.com」並加聲明「與 Meta 無關」。 | 改名。例如用「脆」相關的中文名（Threads 在台灣俗稱「脆」，但這也只是我的建議，要自己確認不撞名）。 |
| 五個功能同在一個插件 | 品質規範要求「單一用途，狹窄且容易理解」；不相干的功能應拆成不同插件。 | 見 1.2。 |
| 權限：`storage`、`downloads`、`https://www.threads.com/*` | 規則要求「最小必要權限」，被判過多會收到 Purple Potassium。Jeff 的 host 權限已經很窄（單一網域），是好事。`downloads` 屬審查會多看的敏感權限，要在後台寫清楚為什麼要。 | 若匯出改成雲端同步，`downloads` 可以拿掉，審查更好過。 |
| `page-hook.js`（主世界偷聽 `/api/graphql` 的回應） | MV3 不禁止，但「全部功能必須能從提交的程式碼看出來」，不能遠端載邏輯。審查員看到攔截第三方網站網路回應會細看。 | 保留可以，但在審查說明裡明講「只讀使用者當下頁面已收到的資料、不發出任何額外請求」。 |
| 高流量自動收集、搜尋頁自動抄趨勢 | 「Limited Use」規則涵蓋「爬來的內容或自動蒐集的使用者資料」，要在商店頁與介面顯眼說明，資料只能用在揭露的單一用途。 | 要嘛當成「進階功能」顯眼揭露，要嘛拆掉。見 1.2。 |
| 隱私政策 | 只要「處理使用者資料」就要有可公開連結的隱私政策，內容要講清楚蒐集什麼、怎麼用、跟誰分享。收錄的貼文存在本機，仍算處理資料，建議當作需要。 | 寫一頁隱私政策，放 Jeff 的 Cloudflare Pages。另外規則要求網站上有「符合 Limited Use」的肯定聲明。 |
| 資料傳輸 | 若有上傳雲端，傳輸要用現代加密（HTTPS），並在上架前揭露、取得使用者明確同意。 | 見第三節。 |

### 1.2 建議的「可上架精簡版」範圍

單一用途寫成：**「在 Threads 貼文下顯示互動率，並讓使用者收藏貼文做文案參考。」**

| 功能 | 精簡版 |
|---|---|
| 互動率顯示 | 留（核心，主要靠 DOM，不靠攔截也能用，只是數字會有「≈」） |
| 文案收錄（使用者手動按） | 留（使用者主動操作，最好解釋） |
| 自己貼文觀看數（洞察報告頁） | 留（讀的是使用者自己的資料） |
| 高流量自動收集 | 拿掉，或改成預設關閉、由使用者手動開 |
| 搜尋頁趨勢話題自動抄 | 拿掉（自動化蒐集色彩最濃，且每日串要靠它） |
| 影片下載 | 拿掉 |
| 每日主題串 | 本來就不在插件裡，是 Jeff 自己的 Claude Code 排程，不受影響 |

也就是上架版會比 Jeff 自用版弱。Jeff 自己繼續用現在的完整版（載入未封裝），商店版另外維護一份，兩份程式要同步改選擇器，是額外的維護成本。

### 1.3 申請與審查流程

- 開發者帳號：一次性註冊費 US$5（約 NT$160），一個帳號可上架多個插件。這個金額來自 2020 年的新聞報導，Google 官方註冊頁沒列金額，付款前以官方頁面為準（待確認）。官方註冊頁另外提醒：帳號 email 不能事後改，也不能重用剛刪除的帳號 email。
- 審查時間：多數幾天內，可能到幾週；超過三週可聯絡開發者支援。新開發者、新插件、含敏感權限，都會讓審查變長。每次更新也會審，所以 Threads 改版後的緊急修復會比現在「重新載入」慢很多。
- 常見被拒原因（商店用「顏色＋元素」編號通知）：
  - Purple Potassium：權限過多或沒用到。
  - 單一用途不清楚、描述誤導、圖示或中繼資料誤導。
  - 隱私政策缺漏或與實際行為不符。
  - 遠端程式碼（MV3 不得執行遠端字串；Jeff 目前沒有這個問題）。
  - 重複上架功能一樣的插件（垃圾與濫用條款）。
- 要準備的上架素材（尺寸是我記憶中的常見規格，待確認）：128px 圖示、至少 1 張 1280×800 截圖、440×280 小型宣傳圖、商店描述（中英）、單一用途說明、每個權限的理由、隱私政策網址、聯絡 email。
- 發布可見度有「公開／不公開（連結才看得到）／指定測試者」三種，這次沒查官方頁面，待確認；我的理解是「不公開」仍然要過同一套審查。
- 若在歐盟地區上架，Google 會要求開發者宣告是否為「商家（trader）」，Jeff 若以公司（沃瀧居）名義上架就要想清楚；以個人免費發布通常不算商家，但要看當時後台怎麼問（待確認）。

## 二、法律與政策風險

### 2.1 Meta／Threads 的規定

我查到的與讀法（Threads 本身的補充條款原文這次沒抓到，下面主要是 Meta／Instagram 通用條款，Threads 條款已知是引用它們，待確認）：

- Meta 條款：不得以自動化方式存取或蒐集資料，未經 Meta 事前許可不行；2024 年 11 月明確加上「不論是否登入都適用」。同時禁止規避 Meta 的存取限制。
- Meta「自動化資料收集條款」（2024-10-07 生效）：
  - 自動化資料收集的定義包含爬蟲、機器人、spider、user-agent 等「直接從網頁或 App 取得內容」的工具。
  - 一律需要 Meta 另行書面許可；僅同意使用條款不算。
  - 取得的資料不得轉讓、出售、授權（含衍生資料），不得用來做商業搜尋服務；不得蒐集非公開個資；不得無視 robots.txt。
  - 條文沒有為「瀏覽器擴充功能」或「使用者自己的資料」另設例外。
- 對 Jeff 的意義（我的讀法）：
  - 完整版裡「滑到就自動記進高流量.json」「搜尋頁每 3 秒自動抄趨勢」「攔截 GraphQL」這些，比較像「自動化蒐集」。
  - 「使用者手動按收錄」「畫面上顯示互動率」比較像一般瀏覽輔助，爭議小很多，但條文沒給明確保證。
  - 把蒐集到的別人貼文放進共用資料池再給其他使用者看，會直接撞上「不得轉讓／授權衍生資料」。
- 法院判例的方向：2024-01 的 Meta v. Bright Data（美國北加州聯邦地方法院）判 Meta 敗訴，理由是對方「未登入」抓公開資料，不算在「使用」Facebook／Instagram，所以條款不適用。**但這正好反過來**：Jeff 的插件是在使用者**登入狀態**下運作，恰好落在條款適用範圍內，所以這個判決對 Jeff 幫助有限。它也只是地區法院、只談契約，未涵蓋其他法律主張，我也沒查到後續上訴結果（待確認）。
- Meta 官方給的合法管道是 Threads API：可以做關鍵字搜尋，但要申請 `threads_keyword_search` 權限並通過審核，上限為每位使用者每 24 小時 2,200 次查詢（官方文件 2026-01-21 更新）。API 提供「貼文搜尋」，我沒在文件中看到「最新趨勢話題清單」這種東西（待確認），所以每日串的趨勢段無法靠官方 API 取代。

| 案例 | 內容 | 對 Jeff 的參考 |
|---|---|---|

| 其他（伊斯坦堡開發者、新澤西行銷公司，2021 年報導提及） | Meta 也告過，但這次沒查到細節。 | — |

**沒查到的**：我沒找到 Meta 針對「Threads 專用瀏覽器擴充功能」提告或要求下架的公開案例，也沒找到因使用這類插件被封帳號的可靠報導。商店上目前有多個 Threads 抓取插件（例如 *Threads Scraper - Data Exporter*，2026-05-29 更新、88 位使用者；*T-Feeds Scraper*；*Threads Engagement Automation*），代表 Google 審查會過；但這不代表 Meta 允許。帳號被停權的報導，多數來源是部落格或廠商文案，可信度低，我不當證據用。

### 2.3 Chrome 商店本身的下架風險

- 用 Logo 當圖示、名稱含商標：Meta 一旦投訴，商店可直接下架，而且依 2021 年一份公開的下架通知範例，之後同一個插件不得重新上架，只能換套件名稱發新版；重複違規可能連整個開發者帳號停權。（這是單一案例，現行流程可能不同。）
- 影片下載：見 1.1，建議拿掉。
- 提醒：有針對開發者的假「著作權申訴」釣魚信，收到下架通知要從開發者後台確認，不要點信裡的連結登入。

### 2.4 個資（台灣個資法，若公開服務才更要注意）

- Threads 貼文內容加作者帳號，屬於可識別特定人的個人資料。
- 台灣個資法：非公務機關蒐集個資須有特定目的，並符合法定事由之一，包括「當事人自行公開或已合法公開」「取自一般可得之來源」，但當事人若有更值得保護的重大利益則不適用。利用要在特定目的必要範圍內。從非當事人處取得資料，原則上要告知來源，但有公開資料的免告知例外，細節我只拿到片段，要以現行條文為準（待確認）。
- 「自然人為單純個人或家庭活動目的」依個資法不在適用範圍（我的記憶，第 51 條，本次未查證，待確認）。**Jeff 自用屬於這類；一旦做成對外提供的服務、尤其是以公司名義，就不屬於了。**
- 歐盟使用者：商店是全球上架，只要有歐盟使用者就可能有 GDPR 義務（蒐集範圍、刪除權、資料處理主體）。這次沒深查（待確認）。
- 自己的觀看數屬於使用者自己帳號的資料，風險低；但仍要在隱私政策揭露。

### 2.5 風險彙整

| 做法 | Meta 條款風險 | 商店風險 | 個資風險 |
|---|---|---|---|
| A. 現況：自用，載入未封裝 | 低到中（技術上仍違反字面，但沒有公開曝光） | 無 | 低（單純個人活動） |
| B. 精簡版，不公開或 zip 給幾位朋友 | 低到中 | 低 | 低 |
| C. 精簡版公開上架 | 中（曝光度上升，容易被注意） | 低到中（要過審；商標要處理乾淨） | 中（你成了資料蒐集主體） |
| D. 完整版（含自動收集、影片）公開上架 | 高 | 高（影片下載、自動蒐集） | 中到高 |
| E. 雲端共用資料池，使用者互看別人收的 | 高（不得轉讓衍生資料） | 中 | 高 |

### Jeff 要決定的事（第二節）

## 三、雲端化：架構草圖、個資、成本

### 3.1 先釐清「雲端化」到底要解什麼

| 想解的問題 | 單機版現況 | 上雲後 |
|---|---|---|
| 換電腦、多台電腦合併資料 | 資料在 chrome.storage，匯出到 Chrome 下載資料夾 | 登入後資料跟著帳號走 |
| 每日主題串 | 靠 Claude Code 桌面版開著，用 Chrome 開 `/search` 抄趨勢 | 雲端排程產生，Mac 不用開 |
| 給別人用 | 每個人要自己架檔案路徑、設定 Chrome 下載 | 登入即用 |
| 檔案路徑麻煩（今天踩的「下載前詢問」「Downloads 路徑」坑） | 要手動設捷徑 | 沒有這問題 |

**重要限制**：雲端排程沒辦法自己去抓 Threads（伺服器端爬取沒有登入、一定被擋，而且更直接違反自動化條款）。所以趨勢話題仍然要靠使用者的瀏覽器某天開過 `/search`，由插件上傳。換句話說，「Mac 完全不用開」做不到，每日串只能用「前一天使用者瀏覽時上傳的資料」來產。

### 3.2 架構草圖（用 Jeff 現有的 Cloudflare Worker + Supabase）

```
Chrome 插件（MV3）
  ├─ content.js / page-hook.js    讀貼文、算互動率（維持在本機）
  ├─ background.js                本機先存，批次上傳（每 N 分鐘或每 50 筆）
  └─ 登入：Supabase Auth（Google 或 Email magic link）
           拿 JWT，存 chrome.storage.session

          │ HTTPS + JWT
          ▼
Cloudflare Worker（API 閘道）
  ├─ POST /ingest   驗 JWT → 驗欄位白名單 → 限流 → 寫入 Supabase
  ├─ GET  /me/...   取回自己的收錄、高流量、趨勢
  ├─ DELETE /me     刪除全部資料
  └─ Cron Trigger   每天 ~08:50 → 為每位使用者取前一天資料 → 呼叫 LLM → 存「每日串」

          ▼
Supabase（Postgres + Row Level Security）
  saved(user_id, code, url, author, posted_at, text, likes, replies, reposts, shares, saved_at, note)
  hot(user_id, code, ... 同上)                -- 每位使用者各自一份
  trends(user_id, date, title, summary, count, url)
  views(user_id, code, views, seen_at)
  daily(user_id, date, markdown)
  RLS：每張表 user_id = auth.uid()，使用者只能讀寫自己的列

          ▼
Jeff 的桌面：threads-funnel 技能改讀 GET /me/saved（或仍讀本機匯出檔）
```

設計要點：

- **每位使用者各一份**，不做共用池（理由見第二節）。同一篇貼文不同人收錄就是不同列。
- 欄位白名單：不上傳頭像、追蹤數、留言者、完整個人檔資料。作者只存帳號字串。
- 插件先本機存、再批次上傳，離線或 API 掛了不影響使用。
- 每日串要呼叫 LLM（Anthropic API）：Worker 需要一把 API key，存在 Worker secret；MV3 規定的「不得遠端程式碼」不受影響，因為這在伺服器端。
- 插件端的新增權限：`identity`（若用 Google 登入）；`host_permissions` 要加 Worker 的網域。每多一項，審查就多一項要解釋的東西。
- Jeff 現有經驗：Walllong 已有 Cloudflare Worker + Supabase、有每 6 小時的 keepalive cron；FTS 的 Supabase 免費專案曾暫停。可沿用同樣的做法與慣例。

另一條路（較省事）：只服務 Jeff 一人時，用 **Cloudflare D1** 取代 Supabase，不會因閒置被暫停，也不佔 Supabase 免費版的 2 個專案名額；缺點是沒有現成的登入／RLS，單人用的話 Worker 以固定金鑰驗證即可。

### 3.3 個資處理

| 資料 | 性質 | 處理 |
|---|---|---|
| 別人的公開貼文內文、作者帳號 | 可識別個人的個資（公開來源） | 只存使用者自己瀏覽過的；每位使用者隔離；保留期限預設 90 天（高流量與趨勢）；收錄由使用者決定；提供一鍵刪除全部；隱私政策明列；不賣、不做廣告、不當 AI 訓練素材 |
| 自己的觀看數、洞察數字 | 使用者自己的資料 | 加密傳輸；僅本人可讀；刪帳號時一併刪 |
| 使用者登入識別（email、user id） | 個資 | 由 Supabase Auth 管；隱私政策說明用途；不與第三方分享 |
| 每日串內容 | 衍生資料 | 同樣只給本人；不對外公開頁面 |
| 日誌 | 可能含 IP | Worker 預設的請求日誌，保留期短；不另外記內文 |

要做到的最小配套：隱私政策頁、同意畫面（首次登入前說明會上傳什麼）、刪除與匯出介面、資料處理主體（Jeff 或沃瀧居）與聯絡 email。

### 3.4 成本

下面價格都來自官方頁面（2026-10-16 查），換算新台幣是我抓約 1 美元 = 32 元的粗估。

| 項目 | 單人（Jeff 自用） | 小規模公開（假設 50～100 人） |
|---|---|---|
| Chrome 開發者帳號 | 不需要 | US$5 一次性（約 NT$160） |
| Cloudflare Workers | 免費方案：每天 10 萬次請求、5 個 Cron、單次 CPU 10 ms（官方）。單人綽綽有餘；每日串要呼叫 LLM、可能超過 10 ms CPU，等待 API 回應通常不計 CPU 時間（待確認），不夠就升級。 | 付費方案最低每月 US$5，含 1,000 萬次請求；超過每百萬 US$0.30 |
| 資料庫（二選一） | **D1 免費**：5 GB、每天讀 500 萬列、寫 10 萬列。**或 Supabase 免費**：500 MB、1 週沒活動會暫停、最多 2 個啟用專案（Jeff 已有其他專案時可能不夠）。 | **Supabase Pro 每月起 US$25（約 NT$800）**，含 8 GB、$10 運算額度（涵蓋一台 Micro）、10 萬 MAU、250 GB 傳輸 |
| LLM（每日串） | 每天 1 次，用 Anthropic API 計費；一次輸入約 1 萬 token、輸出約 2 千 token 的量級，**每月大約幾十分之一美元到數美元**（我沒查現行價格，依 claude-api 的實際計價再算，待確認）。也可以維持現在 Claude Code 桌面排程，費用是 0 | 每人每天一次，約線性成長；可以設為「使用者手動按才產」，或用較小的模型 |
| 網域、隱私政策頁 | Cloudflare Pages 免費；網域自有可免費用子網域 | 同左 |
| **合計** | **NT$0（可行）** | **約 NT$1,000／月起**（Workers $5 + Supabase $25 ≈ US$30）＋LLM 用量 |

儲存量估算（我的算法）：一篇約 2 KB（含內文與索引），每人每天收 300 篇 → 一年約 220 MB。免費 500 MB 的 Supabase 一人大約撐一年；公開幾十人就一定要升級，或改成保留 90 天自動清。

隱形成本：客服（有人登不進去、資料不見）、Threads 改版時全員同時壞掉、商店審查往返、隱私與刪除請求。這些我沒法用金額估，但都是自用版完全沒有的。

### 3.5 建議的分階段做法

1. **階段 0（現況）**：本機儲存加匯出，維持。
2. **階段 1（只給 Jeff）**：Worker＋D1 或 Supabase，單一使用者，登入走固定金鑰；插件加「同步」開關、預設關；每日串搬到 Cron。不上架，不增加審查負擔。約 1～2 天。
3. **階段 2（給身邊少數人）**：加 Supabase Auth 與 RLS，使用者各自隔離，以 zip／不公開連結發。需要同意畫面與刪除功能。
4. **階段 3（公開上架）**：先決條件是第一、二節的決定都「是」。

### Jeff 要決定的事（第三節）

1. 雲端化的主要目的是哪個：換電腦、每日串不用開機、還是給別人用？（目的不同，做到哪一階段就不同）
2. 同意「每位使用者資料互相隔離、不做共用資料池」嗎？（放棄了「大家一起累積高流量清單」的誘因，換取風險降低）
3. 單人階段用 D1 還是 Supabase？（D1 不會被暫停、不佔專案名額；Supabase 以後擴充登入／RLS 較省事）
4. 每日串要不要搬到雲端、改用 Anthropic API 計費？還是維持 Claude Code 桌面排程（零額外費用，但要開機）？
5. 預算上限：若要走小規模公開，可接受每月約 NT$1,000 加 LLM 用量嗎？
6. 保留期限（我建議高流量與趨勢 90 天）與資料主體（Jeff 個人或沃瀧居）怎麼定？
